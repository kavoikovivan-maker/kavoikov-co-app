# Полный запуск и проверка агентной команды

## 1. Цель документа

Этот документ объединяет всё в один полноценный рабочий сценарий для командной работы агентов. Он нужен, чтобы:

- запускать команду как целостную систему;
- исключить хаос и расплывчатые решения;
- проверить каждый элемент работы до завершения;
- закрывать этапы только после доказуемой верификации;
- обеспечить реальный, а не формальный запуск.

## 2. Главный принцип

Команда не стартует по “ощущению”, а запускается по строгому протоколу:

1. Проверить задачу.
2. Зафиксировать ограничения.
3. Назначить роли.
4. Выполнить этапы по порядку.
5. Проверить каждый элемент.
6. Закрыть этап только после PASS.
7. Если QA не пройдена — вернуть на доработку.
8. Только после этого запускать финал.

Никакая стадия не считается завершённой без явной проверки.

## 3. Базовые ограничения запуска

Перед стартом команда должна зафиксировать:

- цель проекта;
- доступные инструменты;
- условия среды;
- список запретов;
- допустимые ресурсы;
- критерии успешного завершения;
- формат итогового результата.

### Обязательные проверки до запуска

- это локальная задача или требуется внешний сервис;
- есть ли платные инструменты;
- есть ли внешние зависимости;
- есть ли ограничения по времени и ресурсам;
- есть ли точный критерий приема;
- есть ли список ошибок, которые нельзя допускать.

Если хотя бы один из этих пунктов не зафиксирован — запуск считается невалидным.

## 4. Роли и зоны ответственности

### 4.1. Coordinator

Ответственность:

- определить порядок работы;
- назначить роли;
- установить этапы;
- контролировать ход;
- отслеживать конфликты между ролями;
- остановить работу, если задача начинает уходить в сторону.

Проверка Coordinator:

- есть ли последовательность этапов;
- есть ли критерии выбора;
- есть ли контроль расхождений;
- есть ли фиксированные блокеры;
- есть ли итоговый список решений и рисков.

### 4.2. Researcher

Ответственность:

- сформировать гипотезы;
- оценить реальность идеи;
- отделить факты от предположений;
- найти риски и неопределённости;
- указать, что можно проверить сейчас, а что требует внешних данных.

Проверка Researcher:

- есть ли список гипотез;
- есть ли оценка реальности;
- отмечены риски;
- есть ли ясное разделение между фактами и допущениями;
- заявлены фактические ограничения.

### 4.3. Author

Ответственность:

- сделать идею понятной;
- описать аудиторию и ценность;
- показать отличие от конкурентов;
- объяснить, почему идея может продаваться.

Проверка Author:

- есть ли ясное название и описание;
- есть ли целевая аудитория;
- есть ли ценность без маркетинговой воды;
- есть ли отличие от конкурентов;
- есть ли понятный, короткий и логичный текст.

### 4.4. Developer

Ответственность:

- оценить реалистичность запуска;
- выделить MVP и блокеры;
- отличить prototype, MVP и full product;
- определить минимальный путь до запуска.

Проверка Developer:

- есть ли разделение по уровням зрелости;
- есть ли список мини-задач;
- есть ли реальный путь запуска;
- указаны риски и препятствия;
- нет ложной оптимистичности.

### 4.5. Reviewer

Ответственность:

- выбрать лучшую идею;
- проверить, что решение действительно подходит;
- указать, чего не хватает для запуска;
- дать финальный вердикт по качеству решения.

Проверка Reviewer:

- выбран вариант по критериям, а не по симпатии;
- есть ли объективные причины выбора;
- перечислены блокеры;
- указан статус: PASS, FAIL или NEEDS_WORK.

## 5. Полный запуск команды

### Этап 0. Preflight

Coordinator:
- фиксирует тему и цели;
- проверяет, есть ли ограничения;
- раскрывает список запрещённых действий;
- задаёт критерии приёмки;
- назначает порядок ролей.

Обязательные вопросы:

- Что задача?
- Что нельзя делать?
- Какие ресурсы и инструменты доступны?
- Что покажет, что работа успешна?
- Что будет считаться блокером?

Если ответы не ясны — запуск стоп.

### Этап 1. Анализ и планирование

Coordinator + Researcher:
- собирают исходный контекст;
- фиксируют ключевые ограничения;
- формируют список гипотез.

Проверка этапа:

- есть ли список гипотез;
- есть ли ограничения;
- есть ли факт vs предположение;
- есть ли список того, что надо проверить.

### Этап 2. Исследование реальности

Researcher:
- оценивает спрос, боль, риск и реалистичность;
- определяет, что можно подтвердить сейчас;
- определяет, что требует внешних данных;
- отмечает несоответствия.

Проверка этапа:

- есть ли конкретная оценка боли;
- есть ли реальная проблема;
- есть ли список внешних зависимостей;
- есть ли различие между “гипотезой” и “фактом”.

### Этап 3. Сбор предложений

Author:
- делает 3–5 вариантов по реальности и формулировке;
- фиксирует ценность и целевую аудиторию;
- формирует короткие и понятные описания.

Проверка этапа:

- есть ли формулировка ценности;
- есть ли аудитория;
- есть ли указание на отличие от конкурентов;
- есть ли понятность текста.

### Этап 4. Оценка запуска

Developer:
- оценивает MVP;
- выделяет prototype, MVP и full product;
- задаёт минимальные требования к запуску;
- фиксирует основные блокеры.

Проверка этапа:

- есть ли минимальный путь запуска;
- есть ли блокеры;
- есть ли честная оценка сроков;
- есть ли отличие между “можно сделать” и “надо сделать”.

### Этап 5. Финальная верификация

Reviewer:
- выбирает лучший вариант;
- сравнивает варианты по критериям;
- фиксирует блокеры и условия запуска;
- даёт итоговый вердикт.

Проверка этапа:

- есть ли причина выбора;
- есть ли списки преимуществ и рисков;
- есть ли соответствие критериям;
- есть ли принятое решение без конфликтов.

### Этап 6. Финальное закрытие

Coordinator:
- собирает выводы всех ролей;
- формирует единую итоговую сводку;
- фиксирует статус проекта;
- говорит, что готово, а что необходимо доработать.

Проверка этапа:

- есть ли единый итог;
- нет ли противоречий между ролями;
- есть ли финальный статус;
- есть ли список блокеров;
- есть ли следующий шаг после запуска.

## 6. Полный QA-блок вопросов

Каждый этап должен пройти проверку по этим вопросам:

1. Что именно нужно сделать?
2. Какие ограничения существуют прямо сейчас?
3. Какой результат должен быть на выходе?
4. Какие есть входные данные?
5. Что можно проверить прямо сейчас?
6. Что не подтверждено?
7. Какие риски и блокеры есть?
8. Что является PASS, а что FAIL?
9. Что ещё нужно решить, чтобы этот этап считался завершённым?
10. Есть ли скрытая допущенность, которую нужно убрать?

Если агент не отвечает на 2 и более пунктов чётко — статус этапа = NEEDS_WORK.

## 7. Критерии статусов

### PASS

Этап считается успешно выполненным, если:

- чётко описана цель;
- соблюдены ограничения;
- результат проверяем;
- есть фактические основания;
- нет скрытых допущений;
- доказана готовность к следующему шагу.

### FAIL

Этап не проходит, если:

- решения расплывчаты;
- нет верификации;
- есть скрытые предположения;
- есть реальный риск, который не указан;
- этап не соответствует задаче или ограничениям.

### NEEDS_WORK

Этап требует доработки, если:

- часть данных отсутствует;
- проверка не завершена;
- есть сомнения, но нельзя назвать это качественной готовностью;
- один или несколько ключевых аргументов не подтверждены.

### BLOCKED

Этап блокируется, если:

- нет необходимых данных;
- есть критическая зависимость извне;
- повторная работа не даёт результата;
- команда истекла лимит попыток.

## 8. Полный прогон команды в формате запуска

```text
Запуск команды:

1. Coordinator:
   - зафиксировать цель и ограничения;
   - назначить роли и порядок;
   - сказать, как будет проходить верификация.

2. Researcher:
   - сформировать гипотезы;
   - определить реальность и риски;
   - указать, что можно подтвердить сейчас.

3. Author:
   - описать предложения в понятной форме;
   - сформировать аудиторию и ценность;
   - объяснить, почему это может продаваться.

4. Developer:
   - определить MVP;
   - выделить prototype, MVP и product;
   - считать минимальный путь запуска.

5. Reviewer:
   - выбрать лучший вариант;
   - указать реальные блокеры;
   - определить финальный статус.

6. Coordinator:
   - собрать единую сводку;
   - зафиксировать итоговой результат;
   - указать, что готово, а что требует доработки.

7. Final QA:
   - проверить все этапы по вопросам;
   - подтвердить статус PASS, FAIL или NEEDS_WORK;
   - завершить работу только после верификации.
```

## 9. Проверка зрелости команды

Команда считается зрелой, если:

- все роли знают свою ответственность;
- task handoff проходит по шаблону;
- отсутствуют скрытые допущения;
- каждый этап проходит QA;
- финальный вывод основан на доказательствах, а не на риторике;
- блокеры зафиксированы заранее и не замалчиваются.

## 10. Полный финальный критерий готовности

Работа считается завершённой только при соблюдении всех условий:

- есть вход и цель;
- есть ограничения и запреты;
- есть понятная роль каждого агента;
- правильно выполнены этапы;
- все ключевые вопросы закрыты;
- есть финальная верификация;
- нет незаписанных блокеров;
- итоговое решение соответствует критериям качества.

Только в этом случае команда готова к реальному запуску и реальной работе.
