# Live Test Run для агентной команды

## 1. Цель тестового прогона

Этот сценарий нужен, чтобы проверить, что команда реально работает как управляемая система, а не как набор красивых ответов. Мы запускаем полный цикл по реальной задаче и проверяем каждый этап по строгим вопросам.

## 2. Тестовая задача

Задача:

> Предложить 3 идеи для iPhone и выбрать лучшую. Использовать только локальные ресурсы. Не подключать платные сервисы. Описать, что можно реально запустить в короткий срок, и что ещё нужно проверить перед запуском.

## 3. Предпусковая проверка

### Обязательные проверки до старта

- задача чётко сформулирована;
- есть ограничения среды;
- платные сервисы запрещены;
- цель понятна;
- есть критерий выбора лучшей идеи;
- есть формат итогового ответа;
- есть фиксированные роли.

### Принятый стартовый статус

Status: READY

## 4. Роли и их входы

### 4.1. Coordinator

Роль: управляет процессом и следит за порядком.

Prompt:

```text
Вы — Coordinator. У вас есть задача: предложить 3 идеи для iPhone, выбрать лучшую и зафиксировать критерии выбора. Работаем строго по этапам: Researcher → Author → Developer → Reviewer. Не допускайте расхождений между этапами. Сначала зафиксируйте ограничения и критерии выбора. После этого запускайте следующий этап только после подтверждения предыдущего. Итог должен содержать: 3 идеи, лучшую идею, критерии выбора, список блокеров и список того, что ещё нужно проверить.
```

Проверка Coordinator:

- есть ли порядок этапов;
- есть ли ограничения;
- есть ли критерии выбора;
- есть ли контроль проблем между ролями.

### 4.2. Researcher

Роль: проверяет реальность идеи.

Prompt:

```text
Вы — Researcher. Сформулируйте 3 гипотезы для iPhone-аудитории. Для каждой идеи оцените: реальную проблему, ценность, спрос, риски, перспективы, что можно проверить локально прямо сейчас, а что требует внешних данных. Не выдавайте фантазию за факт. Отделяйте гипотезу от подтверждённого утверждения.
```

Проверка Researcher:

- есть ли 3 идеи;
- есть ли отличия между фактом и гипотезой;
- есть ли список риска;
- есть ли описание, что можно подтвердить сразу;
- есть ли список неопределённостей.

### 4.3. Author

Роль: превращает идею в понятное предложение.

Prompt:

```text
Вы — Author. Возьмите 3 идеи и преобразуйте их в понятные предложения. Для каждой идеи укажите:
- название;
- проблема;
- целевая аудитория;
- ценность;
- отличие от конкурентов;
- почему это может продаваться.
Пишите ясно, без маркетинговой воды и без красивых слов без сути.
```

Проверка Author:

- есть ли аудитория;
- есть ли реальная ценность;
- есть ли понятное и короткое описание;
- есть ли отличие от конкурентов;
- нет ли “красивого текста без смысла”.

### 4.4. Developer

Роль: оценивает реалистичность и запуск.

Prompt:

```text
Вы — Developer. Для каждой идеи оцените: минимальный MVP, что реально можно сделать за 1–2 недели, что будет блокировать запуск, что относится к prototype, MVP и full product. Разделите: можно сделать быстро, что нужно для запуска, что можно отложить. Будьте честны по ограничениям.
```

Проверка Developer:

- есть ли разделение prototype / MVP / full product;
- есть ли реальный мини-путь запуска;
- есть ли блокеры;
- есть ли пункты “что можно сделать сейчас”, “что отложить”.

### 4.5. Reviewer

Роль: выбирает победителя и даёт финальный вердикт.

Prompt:

```text
Вы — Reviewer. Выберите лучшую идею по критериям: ценность, простота запуска, монетизация, реалистичность, риск. Укажите, чего явно не хватает для запуска, если чего-то не хватает. Не подменяйте факты оптимизмом. Дайте итоговый вердикт: PASS / NEEDS_WORK / BLOCKED.
```

Проверка Reviewer:

- выбран вариант по критериям;
- есть ли причина выбора;
- есть ли список блокеров;
- есть ли честная оценка запуска.

## 5. QA-опрос по всем этапам

Каждый этап должен пройти следующие вопросы:

1. Что именно нужно сделать?
2. Какие ограничения есть?
3. Что является входом, а что выходом?
4. Какой критерий показывает, что задача выполнена?
5. Что можно проверить прямо сейчас?
6. Что ещё не подтверждено?
7. Какие риски и блокеры есть?
8. Что следующий шаг?
9. Что считать PASS / FAIL / NEEDS_WORK?

Если на 2 или более пункта нет чёткого ответа — статус этапа = NEEDS_WORK.

## 6. Результат запуска команды

Ожидаемый итог:

```text
1. 3 идеи для iPhone
2. лучшая идея
3. критерии выбора
4. список блокеров
5. список чего ещё не хватает
6. финальный статус: PASS / NEEDS_WORK / BLOCKED
```

## 7. Форма финального отчёта

```text
# Final Team Report

## Goal
[цель задачи]

## Constraints
[ограничения среды]

## Stage Results
- Coordinator: PASS / NEEDS_WORK / FAIL
- Researcher: PASS / NEEDS_WORK / FAIL
- Author: PASS / NEEDS_WORK / FAIL
- Developer: PASS / NEEDS_WORK / FAIL
- Reviewer: PASS / NEEDS_WORK / FAIL

## Best Idea
[выбранный вариант]

## Why this one
[причины выбора]

## Blockers
[что мешает запуску]

## Remaining Checks
[что ещё важно проверить]

## Final Status
[PASS / NEEDS_WORK / BLOCKED]
```

## 8. Проверка на реальную работоспособность

Команда считается реально работоспособной, если:

- все роли последовательно закрывают этапы;
- нет скрытых предположений;
- нет расплывчатых обещаний;
- всё проходит через критерии;
- финальный статус реально подкреплён проверкой.

Если любой этап не проходит QA — команда не готова к запуску.

## 9. Итоговый критерий

Команда считается готовой к реальной работе только когда:

- все этапы пройдены по порядку;
- все роли отвечают на обязательные вопросы;
- итог вывода подтверждается проверкой;
- блокеры зафиксированы явно;
- нет “магических” решений без данных.

Это и есть живой тестовый прогон команды в рабочем режиме.
