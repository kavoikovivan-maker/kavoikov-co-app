# Runbook для чёткой работы агентной команды

## 1. Назначение

Этот runbook задаёт полный рабочий процесс для команды агентов. Он нужен, чтобы:

- исключить расплывчатый обмен мнениями;
- сделать чёткие ролей и зоны ответственности;
- держать единый порядок работы;
- требовать доказательства на каждом шаге;
- не допускать “принятия решений вслепую”;
- запускать команду как управляемую систему, а не как набор красивых промптов.

## 2. Принцип работы

Команда работает по следующей логике:

1. Зафиксировать задачу и ограничения.
2. Разбить задачу на этапы.
3. Назначить роли и ответственных.
4. Выполнить конкретный этап.
5. Прогнать проверку по вопросам.
6. Если проверка не пройдена — вернуть на доработку с точным feedback.
7. Только после этого перейти к следующему этапу.

Никакое “похоже, это работает” не считается завершением.

## 3. Базовые правила команды

### 3.1. Одна роль — одна зона ответственности

Каждый агент отвечает только за свою область:

- Coordinator — порядок и контроль;
- Researcher — проверка реальности идеи;
- Author — формулировка ценности и предложения;
- Developer — реалистичность запуска и MVP;
- Reviewer — финальная оценка и вердикт.

### 3.2. Запрещено

- работать без фиксированных ограничений;
- пропускать проверку;
- скрывать неопределённости;
- решать задачу “по интуиции”;
- запускать следующий этап без подтверждения предыдущего;
- смешивать анализ, создание и QA в одном сообщении без разметки.

### 3.3. Нормальная работа

Нормальный ответ должен быть:

- конкретным;
- проверяемым;
- привязан к критериям;
- честным по ограничениям;
- ясным по тому, что ещё не подтверждено.

## 4. Единая структура handoff

Каждый агент должен получать задачу в одинаковой форме.

```text
Цель:
[что именно нужно сделать]

Контекст:
[что уже известно, что было решено раньше]

Ограничения:
[что нельзя делать, что запрещено, какие ресурсы доступны]

Вход:
[факты, условия, документы, спецификация, предыдущие выводы]

Ожидаемый результат:
[какой формат ответа нужен]

Критерии приемки:
[что считать успешным результатом]

Проверка:
[какие вопросы должны быть закрыты]

Следующее действие:
[что делать после завершения задачи]
```

Если хотя бы одного пункта нет — handoff считается неполным.

## 5. Этапы рабочей цепочки

### Этап 1. Подготовка

Coordinator:
- фиксирует задачу;
- определяет цель;
- формулирует ограничения;
- назначает роли и порядок;
- задаёт критерии выбора решения.

Проверка:
- есть ли чёткая цель;
- есть ли ограничения;
- есть ли последовательность ролей;
- есть ли критерии выбора.

### Этап 2. Исследование

Researcher:
- формирует гипотезы;
- оценивает спрос, риски и проблемы;
- выделяет факты и предположения;
- фиксирует, что нужно проверить отдельно.

Проверка:
- есть ли реальная проблема;
- есть ли разделение между фактами и предположениями;
- названы риски и зависимости;
- есть ли список проверок.

### Этап 3. Формулировка предложений

Author:
- превращает гипотезы в понятные предложения;
- описывает аудиторию и ценность;
- объясняет, почему это может продаваться;
- показывает отличие от конкурентов.

Проверка:
- есть ли аудитория;
- есть ли ясная ценность;
- понятен смысл идеи без маркетинговой воды;
- есть ли отличие от конкурентов.

### Этап 4. Реалистичность запуска

Developer:
- определяет MVP;
- отличает prototype, MVP и полноценный продукт;
- оценивает сроки и блокеры;
- фиксирует реальные ограничения запуска.

Проверка:
- есть ли минимальный путь запуска;
- есть ли честная оценка сроков;
- названы реальные блокеры;
- нет ложной оптимистичности.

### Этап 5. Финальная проверка

Reviewer:
- выбирает лучший вариант;
- сравнивает варианты по критериям;
- указывает, чего не хватает для запуска;
- говорит, что ещё нужно проверить до старта.

Проверка:
- решение выбрано по критериям, а не по симпатии;
- указаны реальные ограничения;
- есть чёткая причина выбора;
- есть список условий запуска.

## 6. Критерии качества для всех ролей

### Документ считается хорошим, если:

- он отвечает на конкретные вопросы;
- он не размывает мысли;
- он не выдаёт факты за предположения;
- он называет ограничения и риски;
- он указывает, что ещё надо проверить.

### Документ считается плохим, если:

- он красивый, но не проверяемый;
- предлагает идеи без доказательства;
- избегает говорить о блокерах;
- “выбирает победителя” без критериев;
- говорит “всё понятно” без фактов.

## 7. Форма QA-проверки по вопросам

Каждый агент проходит одинаковую проверку:

```text
1. Что именно нужно сделать?
2. Какие ограничения есть прямо сейчас?
3. Что является входом, а что результатом?
4. Какой критерий показывает, что задача завершена?
5. Что можно проверить прямо сейчас?
6. Что ещё не подтверждено?
7. Какие риски и блокеры есть?
8. Что будет следующим шагом?
9. Что считать PASS, а что FAIL?
10. Есть ли явная проблема с качеством или scope?
```

Если агент не отвечает на 2 или более пункта с уверенностью — статус = NEEDS_WORK.

## 8. Статусы процесса

- PLANNED — задача зафиксирована
- IN_PROGRESS — ведётся работа
- QA_PENDING — результат готов, ждёт проверки
- PASSED — проверка подтверждена
- RETRY — есть ошибки, нужна доработка
- BLOCKED — есть критичный блокер
- COMPLETE — все этапы закрыты и финальная проверка прошла

## 9. Правила ретраев

- максимум 3 попытки на задачу;
- после каждой неудачи — точная причина;
- после 3-й неудачи — статус BLOCKED;
- задача возвращается только с конкретным feedback.

## 10. Шаблон каскадной проверки

```text
Сценарий проверки:

Coordinator:
- Что у нас цель, ограничения и порядок?

Researcher:
- Что реально работает, а что лишь гипотеза?

Author:
- Кто аудитория и в чём ценность?

Developer:
- Что реально можно запустить в срок?

Reviewer:
- Что лучшее решение и почему?

Итоговая проверка:
- Есть ли блокеры?
- Есть ли неопределённости?
- Что ещё надо проверить?
- Статус: PASS / FAIL / NEEDS_WORK
```

## 11. Ключевой принцип

Если агент не может объяснить:

- цель;
- ограничения;
- критерий успеха;
- риски;
- что проверено;

то работа не считается готовой.

Это и есть реальная чёткость: не “красиво написано”, а “всё проверено и зафиксировано”.
