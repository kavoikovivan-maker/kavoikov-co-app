# Master Protocol для полноценной работы агентной команды

## 1. Назначение

Этот документ является главным сводным протоколом для всей агентной команды. Он объединяет:

- правила работы;
- порядок запуска;
- распределение ролей;
- передачу контекста;
- процедуры проверки;
- критерии качества;
- правила ретраев и блокировки;
- формат итогового отчёта.

Это не просто набор рекомендаций. Это рабочий стандарт, который команда должна соблюдать на каждом этапе.

## 2. Главная цель команды

Команда должна работать как одна управляемая система, а не как набор независимых мнений. Цель — превращать задачу в результат через строго заданный цикл:

1. Понять задачу.
2. Зафиксировать ограничения.
3. Разбить её на этапы.
4. Назначить роли.
5. Выполнить работу по этапам.
6. Проверить результат по вопросам.
7. Вернуть на доработку при несоответствии.
8. Завершить только после подтверждения качества.

## 3. Необходимые условия запуска

Перед стартом команда должна зафиксировать:

- цель задачи;
- ограничения по среде;
- доступные инструменты;
- запрещённые действия;
- критерии приемки;
- формат финального ответа;
- статус “успешно завершено” и “не завершено”.

Если хотя бы один пункт не зафиксирован — запуск запрещён.

## 4. Принципы работы команды

### 4.1. Один агент — одна область ответственности

Каждый агент работает в своей зоне:

- Coordinator — порядок, координация, контроль и финализация;
- Researcher — маркеты, боли, риски, гипотезы, факт vs предположение;
- Author — формулировка и упаковка идеи;
- Developer — реалистичность запуска, MVP и блокеры;
- Reviewer — финальный вердикт и критерии выбора.

### 4.2. Нет “похоже, нормально”

Нельзя считать результат готовым без проверки.

Подтверждение должно быть через:

- критерии;
- доказательства;
- артефакты;
- проверку по пунктам;
- статусы PASS / FAIL / NEEDS_WORK.

### 4.3. Без скрытых допущений

Если агент предполагает, но не подтверждает — это не готовый вывод. Это неопределённость. Неопределённость должна быть записана отдельно.

### 4.4. Нет scope creep

Дополнительные функции, внешние сервисы и расширение задачи допустимы только если:

- это явно требуется задачей;
- это чётко согласовано;
- это не нарушает ограничения;
- это не увеличивает риск без причины.

## 5. Единый handoff формат

Каждый агент получает задачу в одинаковом формате.

```text
Цель:
[что требуется]

Контекст:
[что уже известно]

Ограничения:
[что запрещено, что доступно, что нельзя менять]

Вход:
[факты, данные, спецификация, предыдущие результаты]

Ожидаемый результат:
[что должно быть на выходе]

Критерии приемки:
[как понять, что задача решена]

Проверка:
[какие вопросы должны быть закрыты]

Следующее действие:
[что делать дальше после завершения]
```

Если одного из блоков нет — handoff считается неполным.

## 6. Структура работы команды

### Этап 1. Понимание задачи

Coordinator:
- фиксирует задачу;
- формулирует цель;
- отмечает ограничения;
- определяет критерии успеха;
- назначает порядок ролей.

Проверка этапа:
- есть ли цель;
- есть ли ограничения;
- есть ли критерии успеха;
- есть ли порядок этапов.

### Этап 2. Анализ и сбор гипотез

Researcher:
- формирует гипотезы;
- оценивает релевантность;
- уточняет рыночную или пользовательскую ценность;
- выделяет факты и допущения;
- определяет, что можно проверить сразу.

Проверка этапа:
- есть ли список гипотез;
- есть ли разделение факт/предположение;
- есть ли список рисков;
- есть ли список вопросов для проверки.

### Этап 3. Формулировка предложения

Author:
- формирует понятное описание;
- фиксирует целевую аудиторию;
- описывает ценность;
- объясняет отличие от конкурентов;
- показывает, почему это может продаваться.

Проверка этапа:
- есть ли аудитория;
- есть ли понятная ценность;
- есть ли логика и отличие;
- нет ли маркетинговой воды без реального смысла.

### Этап 4. Проверка реалистичности запуска

Developer:
- определяет MVP;
- отделяет prototype от MVP и full product;
- фиксирует минимальные действия для запуска;
- отмечает блокеры и ограничения.

Проверка этапа:
- есть ли грамотное разделение по уровням;
- есть ли минимум для запуска;
- есть ли блокеры;
- есть ли строительный путь без завышенных ожиданий.

### Этап 5. Финальная оценка

Reviewer:
- выбирает лучший вариант;
- сравнивает по критериям;
- фиксирует сильные и слабые стороны;
- отмечает, чего не хватает для запуска;
- делает итоговый вердикт.

Проверка этапа:
- выбор сделан по критериям, а не по симпатии;
- есть реальные причины;
- есть список блокеров и условий запуска;
- есть итоговый статус.

### Этап 6. Финальный сводный отчёт

Coordinator:
- объединяет результаты всех ролей;
- формирует единый документ;
- фиксирует итоговый статус;
- перечисляет, что готово и что нужно доработать.

Проверка этапа:
- есть ли единый итог;
- нет ли расхождений между ролями;
- есть ли финальный статус;
- есть ли список дальнейших действий.

## 7. Базовый QA-сценарий для всех участников

Каждый агент должен отвечать на вопросы:

1. Что именно нужно сделать?
2. Какие ограничения есть прямо сейчас?
3. Что является входом, а что результатом?
4. Как понять, что задача выполнена?
5. Что можно проверить прямо сейчас?
6. Что ещё не подтверждено?
7. Какие риски или блокеры есть?
8. Какой следующий шаг после завершения?
9. Что в этом результате может быть ошибочным?
10. Какой статус у этой работы: PASS / FAIL / NEEDS_WORK?

Если ответ на 2 или более пункта расплывчатый — статус = NEEDS_WORK.

## 8. Критерии качества

### PASS

Результат проходит, если:

- задача полностью соответствует цели;
- соблюдены ограничения;
- результат проверяем;
- есть доказательства;
- есть ясные формулировки;
- не осталось критических неопределённостей.

### FAIL

Результат не проходит, если:

- задача решена не по целям;
- есть скрытые допущения;
- нет проверок;
- есть критические риск-факторы;
- вывод выглядит логично, но не подтверждён.

### NEEDS_WORK

Результат требует доработки, если:

- часть данных отсутствует;
- проверка не завершена;
- есть сомнения в ключевом аспекте;
- решение не готово для принятия.

### BLOCKED

Результат заблокирован, если:

- задача зависит от внешнего условия;
- нет необходимой информации;
- лимит повторных попыток исчерпан;
- без изменения условий нельзя добиться корректного результата.

## 9. Политика повторов и эскалации

### Лимит повторов

Каждая задача может быть возвращена на доработку не более 3 раз.

### После третьей неудачи:

- статус меняется на BLOCKED;
- причина фиксируется чётко;
- пишется, чего не хватает для завершения;
- принимается решение: продолжать, перераспределять или остановить этап.

### Эскалация требуется, если:

- нет достаточно данных;
- появляются конфликтующие решения;
- задача выходит за ограничения;
- действия не дают корректного результата;
- качество ниже минимального допустимого уровня.

## 10. Формат финального отчёта

```text
# Итоговый отчёт команды

## Цель
[что было нужно сделать]

## Ограничения
[что было запрещено или ограничено]

## Этапы выполнения
- 1. [этап] — PASS / FAIL / NEEDS_WORK
- 2. [этап] — PASS / FAIL / NEEDS_WORK
- 3. [этап] — PASS / FAIL / NEEDS_WORK

## Результаты ролей
Coordinator:
[вывод]

Researcher:
[вывод]

Author:
[вывод]

Developer:
[вывод]

Reviewer:
[вывод]

## Финальный вердикт
[PASS / FAIL / NEEDS_WORK / BLOCKED]

## Блокеры
[list]

## Что ещё нужно проверить
[list]

## Следующий шаг
[одна конкретная рекомендация]
```

## 11. Ключевое правило

Команда считается готовой только тогда, когда:

- у всех ролей есть конкретная ответственность;
- этапы идут по порядку;
- каждое решение проверено;
- все риски и блокеры записаны;
- итог содержит не “мнение”, а результат верификации;
- командная работа управляется, а не хаотична.

Это и есть реальный максимальный уровень работы агента и команды — не красивый текст, а контролируемый, проверяемый и повторяемый процесс.
